# Alumni Management System — Complete Project Specification

---

## 1. Project Overview

The **Alumni Management System** is a web-based platform designed to strengthen the connection between university alumni and current students through a centralized digital environment. It serves as a bridge where alumni can stay engaged with their alma mater and students can benefit from the experience, mentorship, and network of those who graduated before them.

### Key Project Decisions (Locked)
- ✅ **Payments are mocked** — no real gateway. A simulated "Pay Now" / "Confirm Donation" button instantly marks the transaction as successful.
- ✅ **Admin accounts are invite-only** — new admins can only register using a valid, unused invite code generated by an existing admin. The first admin is seeded directly into the database.
- ✅ **No image uploads** — profiles are fully text-based; no profile pictures, no file uploads anywhere in the system.

### Purpose
- Maintain a centralized, structured record of all alumni, students, and university events.
- Enable students to discover and connect with alumni for mentorship and career guidance.
- Allow the university to organize events (reunions, seminars, workshops) with registration and ticketing.
- Facilitate alumni donations to specific university campaigns and track contribution history.
- Provide administrators with dashboards and reports for engagement analytics.

### Core Value
- **For Students:** Access to a network of experienced professionals for mentorship.
- **For Alumni:** Stay connected with the university, give back through mentorship and donations, attend events.
- **For University/Admin:** Manage alumni engagement, organize events, and track institutional growth.

## 2. Tech Stack

| Layer | Technology |
|---|---|
| **Frontend** | HTML5, CSS3, JavaScript (Vanilla JS, no framework) |
| **Backend** | C# with ASP.NET Core Web API (.NET 8) |
| **Database** | Microsoft SQL Server (MSSQL) |
| **ORM / DB Access** | Entity Framework Core (Code-First or DB-First) |
| **Authentication** | JWT (JSON Web Tokens) |
| **API Communication** | REST API over HTTPS, JSON payloads |
| **Frontend ↔ Backend** | `fetch()` API calls from JavaScript |

### Architecture
```
 [Browser - HTML/CSS/JS]  ←→  [ASP.NET Core Web API]  ←→  [MSSQL Database]
```

- Frontend is fully decoupled from backend. They communicate only via REST endpoints.
- Backend handles all business logic, validation, and database access.
- Database holds normalized data with enforced referential integrity.

## 3. User Roles

The system has **three distinct roles**, each with specific powers and restrictions.

### 3.1 Admin
**Powers:**
- Create, update, and delete events.
- View all alumni, students, mentorship requests, donations, and events.
- Access all dashboards and reports (system-wide analytics).
- Approve or reject alumni registrations (if verification is enabled).
- Create donation campaigns.
- Manage user accounts (deactivate misbehaving users).

**Constraints:**
- Cannot send mentorship requests.
- Cannot make donations (admin is a system role, not a participant).
- Can only be created via **admin invite code** (no open self-registration). See Feature 1 for details.

**Tasks:**
- Monitor platform activity.
- Organize events and campaigns.
- Generate reports on engagement.

### 3.2 Alumni
**Powers:**
- Create and manage their own professional profile.
- Receive and respond (accept/reject) to mentorship requests from students.
- Register for events and purchase tickets.
- Make donations to active campaigns.
- View their own donation history and mentorship history.

**Constraints:**
- Cannot create events.
- Cannot view other alumni's private contact info unless they accept a connection.
- Cannot send mentorship requests (only students can).
- Can only edit their own profile.

**Tasks:**
- Maintain updated professional profile.
- Mentor students when possible.
- Contribute to university growth via events and donations.

### 3.3 Student
**Powers:**
- Create and manage their own academic profile.
- Search and filter the alumni directory.
- Send mentorship requests to alumni.
- Register for events and purchase tickets.
- View their own mentorship request history.

**Constraints:**
- Cannot create events.
- Cannot make donations (donations are alumni-only).
- Cannot view another student's full profile (only alumni profiles are searchable).
- Can only edit their own profile.
- Cannot send multiple pending requests to the same alumnus (must wait for response).

**Tasks:**
- Build network with alumni.
- Attend events and learn from industry professionals.

## 4. Feature-by-Feature Workflows

Each feature below includes its **workflow**, **constraints**, **validation rules**, and **business logic**.

---

### Feature 1: User Registration & Authentication

#### Workflow
1. User lands on the **Landing Page** and clicks **Register**.
2. User selects role: **Student**, **Alumni**, or **Admin**.
   - If **Admin** is selected, an additional field appears: **Admin Invite Code**.
3. User fills the registration form:
   - Full Name, Email, Password, Confirm Password, Role, Phone, Date of Birth
   - (Admin only) Admin Invite Code
4. On submit:
   - Frontend validates fields (format, match, required).
   - Backend checks if email already exists → if yes, return error.
   - If role = Admin → backend verifies the invite code against `AdminInviteCodes` table:
     - Code must exist, not be expired, and not already used.
     - If invalid → registration rejected.
     - If valid → code is marked as used, admin account is created.
   - Password is hashed (BCrypt or ASP.NET Identity hashing).
   - User record is inserted into the `Users` table.
   - For Student/Alumni → a corresponding empty `AlumniProfile` or `StudentProfile` row is created.
5. User is redirected to **Login Page**.
6. On login:
   - User enters email + password.
   - Backend verifies credentials.
   - On success, backend returns a **JWT token** containing `UserId` and `Role`.
   - Frontend stores the token in `localStorage` and attaches it to every subsequent API call as `Authorization: Bearer <token>`.

#### Constraints & Rules
- Email must be unique across the entire system.
- Password must be at least 8 characters, contain one uppercase, one number, and one special character.
- Phone number must be in valid format (configurable, e.g., +92XXXXXXXXXX).
- JWT token expires in 24 hours; user must re-login after expiry.
- Failed login attempts beyond 5 in 15 minutes should temporarily lock the account (optional security feature).
- Passwords are **never** stored in plaintext.
- **Admin invite codes:**
  - Stored in `AdminInviteCodes` table with fields: `Code`, `IsUsed`, `ExpiryDate`, `CreatedBy`, `UsedByUserId`.
  - Each code can only be used once.
  - Codes are generated manually by an existing admin via a hidden endpoint, OR pre-seeded in the database for the very first admin.
  - The **first admin** must be inserted directly into the DB via seed data (bootstrap problem).
  - Subsequent admins are invited by existing admins generating a new code.

### Feature 2: Alumni Profile Management

#### Workflow
1. After first login, alumni are directed to **Complete Profile** page.
2. Alumni fills:
   - Graduation Year, Department, Degree Program
   - Current Company, Job Title, Industry, Work Location
   - LinkedIn URL, Short Bio
3. On save:
   - Backend validates all fields.
   - Data is upserted into `AlumniProfiles` table linked by `UserId`.
4. Alumni can return to profile page anytime to edit.

#### Constraints & Rules
- Graduation year must be a past year (≤ current year) and ≥ 1950.
- Department must match a value from a pre-seeded `Departments` table.
- Only the profile owner (or admin) can edit an alumni profile.
- LinkedIn URL (if provided) must match a valid LinkedIn URL regex.
- **No image uploads** — profiles are text-only for simplicity.

---

### Feature 3: Student Profile Management

#### Workflow
1. After registration, students complete:
   - Enrollment Year, Expected Graduation Year, Department, Degree Program
   - Current Semester, CGPA (optional), Short Bio
2. Save → data goes into `StudentProfiles` table.

#### Constraints & Rules
- Enrollment year ≤ current year.
- Expected graduation year > enrollment year.
- CGPA (if entered) must be between 0.00 and 4.00.
- Only profile owner or admin can edit.

---

### Feature 4: Alumni Directory Search & Filtering

#### Workflow
1. Student logs in and opens **Alumni Directory** page.
2. Directory shows a paginated list of all alumni with basic info (Name, Job Title, Company, Grad Year).
3. Student can apply filters:
   - Department (dropdown)
   - Graduation Year (range or dropdown)
   - Industry (dropdown)
   - Location (text or dropdown)
   - Keyword search (name, company)
4. Backend returns matching alumni.
5. Student can click an alumnus card to view a detailed public profile.
6. From the detail page, student can click **Request Mentorship**.

#### Constraints & Rules
- Only students (and admin) can access the directory.
- Alumni can only see themselves; they don't browse other alumni directory.
- Only **public** profile fields are shown (email and phone hidden unless mentorship is accepted).
- Pagination: 10 or 20 alumni per page.
- Filters can be combined (AND logic).

---

### Feature 5: Mentorship Request Management

#### Workflow
1. Student clicks **Request Mentorship** on an alumni profile.
2. Student writes a short message (reason for request) → submit.
3. A new row is inserted into `MentorshipRequests` table with status = `Pending`.
4. Alumnus sees the request in their **Mentorship Requests** inbox.
5. Alumnus clicks **Accept** or **Reject**:
   - Accept → status becomes `Accepted`. Student is notified. Both can now see each other's contact info.
   - Reject → status becomes `Rejected`. Student is notified.
6. Student can view the status in their **My Requests** page.

#### Constraints & Rules
- A student cannot send a new request to the same alumnus while a previous one is `Pending`.
- A student cannot send a new request to the same alumnus if one was `Accepted` and is still active.
- Only the target alumnus can accept/reject their own incoming requests.
- Message length must be 20–500 characters.
- Once accepted/rejected, the status cannot be reverted.
- Pending requests older than 30 days can be auto-expired (optional).

---

### Feature 6: Event Creation & Management

#### Workflow
1. Admin logs in → opens **Manage Events** page.
2. Admin clicks **Create New Event** and fills:
   - Title, Description, Date, Time, Location, Capacity, Ticket Price, Category (Reunion, Seminar, Workshop, etc.)
3. Save → row inserted into `Events` table.
4. Admin can edit event details until the event starts.
5. Admin can cancel an event (status = `Cancelled`). All registered attendees should be notified.

#### Constraints & Rules
- Event date must be in the future (at least 1 day from today).
- Capacity must be ≥ 1.
- Ticket price must be ≥ 0 (free events allowed with price = 0).
- Only admin can create, edit, or cancel events.
- Cancelled events cannot be re-activated.
- Cannot delete an event that has registered attendees — must cancel instead.

---

### Feature 7: Event Registration & Participation Tracking

#### Workflow
1. Alumni/Student opens **Events** page → sees list of upcoming events.
2. User clicks an event to view details.
3. User clicks **Register** → redirected to ticketing flow (see Feature 8).
4. On successful ticket purchase, a row is inserted into `EventRegistrations`.
5. At/after event time, admin can mark attendees as present (sets `Attended = true`).

#### Constraints & Rules
- A user cannot register twice for the same event.
- Registration closes when capacity is full or when event date has passed.
- Cancellation of registration is allowed up to 24 hours before event time (refund based on policy).
- Admin marks attendance manually, or it can be auto-marked via check-in code.

---

### Feature 8: Event Ticketing System

#### Workflow
1. When a user registers for an event, a ticket is generated.
2. Ticket has:
   - Ticket Code (unique), Event ID, User ID, Price, Payment Status, Issue Date
3. If event is free → payment status = `Paid` automatically.
4. If paid event → user is shown a **simulated payment page** with a **"Pay Now" button**.
   - No real card details collected. No real payment gateway involved.
   - Optional: show mock fields like "Card Number (any)" just for UI realism, but values are not stored or verified.
5. On clicking **Pay Now**, ticket status is set to `Paid` instantly.
6. Ticket is visible in user's **My Tickets** page with a unique ticket code (optionally rendered as a QR code).

#### Constraints & Rules
- Ticket code must be unique (GUID or random alphanumeric).
- One user = one ticket per event.
- Refund on cancellation: 100% if cancelled ≥ 24 hours before; 0% otherwise (refund is just a DB flag update since payment is mocked).
- **Payment is fully mocked** — the "Pay Now" button simulates success with no real transaction. This is acceptable for academic scope.
- No real credit card data should ever be collected or stored.

---

### Feature 9: Donation Management

#### Workflow
1. Admin creates a **Donation Campaign** (Title, Description, Target Amount, End Date).
2. Alumni opens **Donations** page → sees list of active campaigns.
3. Alumni selects a campaign → enters donation amount → clicks **Donate**.
4. A **simulated payment confirmation dialog** appears with a **"Confirm Donation" button**.
   - No real payment gateway. No card details collected.
5. On confirm, donation record is created with status = `Completed`.
6. Campaign's `RaisedAmount` is updated.
7. Alumni can view their donation history in **My Donations**.

#### Constraints & Rules
- Only alumni (not students) can donate.
- Donation amount must be > 0 and ≤ a reasonable max (e.g., 1,000,000 PKR).
- Cannot donate to an expired or inactive campaign.
- Donation history is private to each alumnus (only admin sees all).
- Campaign `RaisedAmount` must never exceed `TargetAmount` (or allow overfunding based on rules).
- **Payment is fully mocked** — clicking "Confirm Donation" simulates instant successful transfer. No real money is processed.

---

### Feature 10: Dashboard & Reporting

#### Workflow (Admin Dashboard)
1. Admin logs in → sees dashboard with summary cards:
   - Total Alumni, Total Students, Total Events, Active Campaigns, Total Donations
2. Visual reports:
   - Mentorship stats (Pending, Accepted, Rejected counts)
   - Event participation (registrations per event, attendance rates)
   - Donation reports (total raised, top donors, per-campaign breakdown)
3. Filters: date range, department, campaign.

#### Workflow (Alumni Dashboard)
- My mentorship requests received (counts by status)
- My upcoming events
- My donation history summary

#### Workflow (Student Dashboard)
- My mentorship requests sent (counts by status)
- My upcoming events
- Suggested alumni (based on my department)

#### Constraints & Rules
- Admin sees **all** data; alumni/student see **only their own** data.
- Reports are generated via SQL aggregation queries (COUNT, SUM, GROUP BY).
- Dashboard should load in reasonable time (optimize queries, use indexes).

## 9. Non-Functional Requirements

- **Security:** Passwords hashed, JWT for auth, SQL injection prevented via EF Core, XSS prevented via frontend sanitization.
- **Performance:** DB indexes on foreign keys and search columns (email, graduation_year, department_id).
- **Validation:** Both client-side (JS) and server-side (C# model validation).
- **Error Handling:** Consistent error response format (e.g., `{ "success": false, "message": "..." }`).
- **Code Quality:** Clean folder structure, meaningful naming, comments where needed, repository pattern for DB access.
- **Usability:** Responsive design (works on desktop + tablet), clear navigation, confirmation dialogs for destructive actions.

## 13. Functional Requirements (Numbered)

Each requirement has a unique ID so it can be referenced in testing, design documents, and reports.

### FR-100 Series: Authentication
- **FR-101** The system shall allow Students and Alumni to register with unique credentials.
- **FR-102** The system shall allow Admin registration only via a valid, unused invite code.
- **FR-103** The system shall authenticate users via email and password.
- **FR-104** The system shall issue a JWT token on successful login, valid for 24 hours.
- **FR-105** The system shall lock an account after 5 failed login attempts within 15 minutes.
- **FR-106** The system shall hash all passwords before storage; no plaintext passwords shall ever be stored.

### FR-200 Series: Profile Management
- **FR-201** The system shall allow each user to edit only their own profile.
- **FR-202** The system shall validate alumni graduation year between 1950 and current year.
- **FR-203** The system shall validate student CGPA between 0.00 and 4.00.
- **FR-204** The system shall validate that a student's expected graduation year is greater than their enrollment year.
- **FR-205** The system shall not support image uploads; all profiles are text-only.

### FR-300 Series: Alumni Directory
- **FR-301** The system shall allow Students and Admins to browse the alumni directory.
- **FR-302** The system shall allow filtering alumni by department, graduation year, industry, location, and keyword.
- **FR-303** The system shall paginate directory results (10 or 20 per page).
- **FR-304** The system shall hide alumni contact info (email, phone) unless a mentorship is accepted.
- **FR-305** The system shall restrict alumni from browsing other alumni in the directory.

### FR-400 Series: Mentorship
- **FR-401** The system shall allow only Students to send mentorship requests.
- **FR-402** The system shall prevent a student from sending a new request to the same alumnus while a previous request is Pending or Accepted.
- **FR-403** The system shall require a mentorship request message of 20–500 characters.
- **FR-404** The system shall allow only the target Alumnus to accept or reject their incoming requests.
- **FR-405** The system shall notify both parties when a request is accepted or rejected.
- **FR-406** The system shall not allow a status change after a request has been Accepted or Rejected.

### FR-500 Series: Events
- **FR-501** The system shall allow only Admins to create, edit, or cancel events.
- **FR-502** The system shall require event date to be at least 1 day in the future at creation time.
- **FR-503** The system shall require event capacity to be at least 1.
- **FR-504** The system shall allow ticket price of 0 (free events).
- **FR-505** The system shall prevent an event from being deleted if it has registered attendees; it can only be cancelled.
- **FR-506** The system shall notify all registered attendees if an event is cancelled.

### FR-600 Series: Event Registration & Ticketing
- **FR-601** The system shall allow authenticated users to register for upcoming events.
- **FR-602** The system shall prevent a user from registering twice for the same event.
- **FR-603** The system shall close registration when the event reaches capacity or after the event date.
- **FR-604** The system shall issue a unique ticket code on successful registration.
- **FR-605** The system shall simulate payment via a "Pay Now" button without collecting real card data.
- **FR-606** The system shall allow registration cancellation up to 24 hours before the event.
- **FR-607** The system shall mark 100% refund for cancellations made ≥24 hours before; 0% otherwise.

### FR-700 Series: Donations
- **FR-701** The system shall allow only Alumni to make donations.
- **FR-702** The system shall allow only Admins to create donation campaigns.
- **FR-703** The system shall require donation amount greater than 0 and less than or equal to 1,000,000 PKR.
- **FR-704** The system shall prevent donations to expired or inactive campaigns.
- **FR-705** The system shall simulate donation payment via a "Confirm Donation" button.
- **FR-706** The system shall update the campaign's raised amount immediately upon donation.
- **FR-707** The system shall allow alumni to view only their own donation history; admins see all.

### FR-800 Series: Dashboard & Reports
- **FR-801** The system shall provide role-specific dashboards (Admin, Alumni, Student).
- **FR-802** The system shall show admins system-wide counts: total alumni, students, events, campaigns, donations.
- **FR-803** The system shall show alumni their received mentorship requests, upcoming events, and total donated.
- **FR-804** The system shall show students their sent mentorship requests, upcoming events, and registered events.
- **FR-805** The system shall generate reports on mentorship statistics, event participation, and donation totals.

## 14. Non-Functional Requirements

### 14.1 Performance
- **NFR-01** Any page shall load within 3 seconds on a standard broadband connection.
- **NFR-02** The alumni directory shall return search results within 2 seconds for a database of up to 10,000 alumni.
- **NFR-03** Dashboard queries shall be optimized with appropriate database indexes.

### 14.2 Security
- **NFR-04** All passwords shall be hashed using a strong algorithm (BCrypt or equivalent).
- **NFR-05** All API endpoints except register/login shall require a valid JWT.
- **NFR-06** The system shall prevent SQL injection via parameterized queries (handled by EF Core).
- **NFR-07** The system shall sanitize user input on the frontend to prevent XSS.
- **NFR-08** The system shall enforce HTTPS in production.
- **NFR-09** JWT tokens shall expire after 24 hours.

### 14.3 Usability
- **NFR-10** The UI shall be responsive and usable on desktop and tablet (minimum width 768px).
- **NFR-11** All destructive actions (cancel event, reject request) shall show a confirmation dialog.
- **NFR-12** Form validation errors shall be shown inline, next to the relevant field.
- **NFR-13** The UI shall show loading indicators for any operation taking more than 500ms.

### 14.4 Reliability
- **NFR-14** The system shall handle all runtime errors gracefully and return a standard error response.
- **NFR-15** The system shall log all errors for debugging.
- **NFR-16** Database integrity shall be enforced via foreign keys and check constraints.

### 14.5 Maintainability
- **NFR-17** Backend code shall follow the Repository pattern and separation of concerns (Controller → Service → Repository).
- **NFR-18** All API endpoints shall return responses in a consistent JSON format.
- **NFR-19** Code shall be organized in the folder structure defined in Section 12.

### 14.6 Compatibility
- **NFR-20** The frontend shall work on the latest versions of Chrome, Firefox, Edge, and Safari.
- **NFR-21** The backend shall run on .NET 8 on Windows, Linux, or macOS.

## 15. Use Cases

Key use cases walking through full actor-system interactions.

### UC-01: Student Sends a Mentorship Request
- **Actor:** Student
- **Precondition:** Student is logged in and has completed their profile.
- **Main Flow:**
  1. Student navigates to Alumni Directory.
  2. Student applies filters (e.g., Computer Science, 2015–2020).
  3. System displays matching alumni.
  4. Student clicks on an alumnus card.
  5. System displays the alumnus's public profile.
  6. Student clicks "Request Mentorship".
  7. System opens a message form.
  8. Student enters message (20–500 chars) and submits.
  9. System validates, creates request with status = Pending, confirms to student.
- **Alternate Flow 8a:** If a pending/accepted request already exists → system blocks submission with an error.
- **Postcondition:** Request appears in student's "My Requests" page and alumnus's inbox.

### UC-02: Alumnus Accepts a Mentorship Request
- **Actor:** Alumnus
- **Precondition:** Alumnus has at least one Pending request in inbox.
- **Main Flow:**
  1. Alumnus opens Inbox.
  2. System lists Pending requests.
  3. Alumnus opens a request to read the message.
  4. Alumnus clicks "Accept".
  5. System shows confirmation dialog.
  6. Alumnus confirms.
  7. System updates status to Accepted, records timestamp.
- **Postcondition:** Student sees status change and can now view alumnus's contact info.

### UC-03: Admin Creates an Event
- **Actor:** Admin
- **Precondition:** Admin is logged in.
- **Main Flow:**
  1. Admin opens Manage Events.
  2. Admin clicks "Create Event".
  3. System displays event form.
  4. Admin fills Title, Description, Category, Date, Time, Location, Capacity, Ticket Price.
  5. Admin clicks Save.
  6. System validates (date in future, capacity ≥ 1, price ≥ 0).
  7. System creates event with status = Scheduled.
- **Alternate Flow 6a:** Invalid input → inline errors, no save.
- **Postcondition:** Event appears in public events list.

### UC-04: Alumnus Makes a Donation
- **Actor:** Alumnus
- **Precondition:** At least one Active campaign exists.
- **Main Flow:**
  1. Alumnus opens Donations page.
  2. System lists active campaigns.
  3. Alumnus clicks a campaign.
  4. System shows campaign details with progress bar.
  5. Alumnus enters amount and clicks Donate.
  6. System shows simulated payment dialog.
  7. Alumnus clicks Confirm Donation.
  8. System records donation, updates campaign RaisedAmount, confirms to alumnus.
- **Postcondition:** Donation appears in "My Donations"; admin sees it in reports.

### UC-05: User Registers for an Event
- **Actor:** Student or Alumnus
- **Precondition:** Event is Scheduled and has available seats.
- **Main Flow:**
  1. User browses Events page.
  2. User clicks on an event.
  3. System shows event details and "Register" button.
  4. User clicks Register.
  5. If free → system registers immediately and issues ticket.
  6. If paid → system shows mock payment page. User clicks Pay Now. System issues ticket.
- **Alternate Flow:** User already registered → button is disabled.
- **Postcondition:** Ticket appears in user's "My Tickets".

## 16. Data Requirements (Conceptual)

This section describes the **conceptual data entities** the system must manage. Detailed table schemas, data types, and constraints belong in the separate **Database Design Document**.

### 16.1 Core Entities
- **User** — A person with access to the system (Student, Alumni, or Admin).
- **Department** — An academic department the university offers.
- **AlumniProfile** — Professional and academic info for an alumnus.
- **StudentProfile** — Academic info for a current student.
- **AdminInviteCode** — One-time code used to register a new admin.
- **MentorshipRequest** — A request from a student to an alumnus for mentorship.
- **Event** — A university event created by admin.
- **EventRegistration** — A user's registration for a specific event.
- **Ticket** — A ticket issued upon event registration.
- **DonationCampaign** — A fundraising campaign created by admin.
- **Donation** — An individual donation made by an alumnus to a campaign.

### 16.2 Key Relationships (Conceptual)
- One **User** has one **AlumniProfile** OR one **StudentProfile** (depending on role).
- One **Department** has many alumni and many students.
- One **Student** sends many **MentorshipRequests**; one **Alumnus** receives many.
- One **Event** has many **EventRegistrations**; one **User** can register for many events.
- One **EventRegistration** has one **Ticket**.
- One **DonationCampaign** receives many **Donations**; one **Alumnus** makes many donations.

### 16.3 Data Retention
- User accounts remain until explicitly deactivated.
- Mentorship requests remain permanently for historical record.
- Cancelled events and closed campaigns remain in the database (not deleted) for reporting.
